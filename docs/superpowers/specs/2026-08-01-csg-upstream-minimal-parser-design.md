# 南网计量上行规约最小解析设计

**状态：** 已确认
**日期：** 2026-08-01
**依据：** 《中国南方电网有限责任公司计量自动化终端技术规范 第5部分：上行通信规约（2026版V1.0）》
**真实样本：** `Terminal3.log`

## 1. 背景

LogAnalyQt 当前支持 DL/T 698、IEC 101、IEC 104、应用层消息、模块消息、Q/GDW 376.2 和 DL/T 645。现需新增“南网计量上行规约”，但第一阶段不追求完整数据字典和智能组帧，只实现一个能够贯通现有日志分析链路的最小解析切片。

第一阶段必须从真实日志中的十六进制报文出发，完成自动识别、帧边界计算、严格校验、公共字段解析、少量数据项解析、字段树展示和全局日志预览。未实现的数据项必须安全降级，不能导致整个合法帧解析失败。

## 2. 目标

第一阶段交付以下能力：

1. 将“南网计量上行规约”作为独立协议加入现有协议枚举与自动检测链路。
2. 识别并校验 `68 L L 68 ... CS 16` 格式的完整链路帧。
3. 解析控制域、7 字节地址域、AFN、SEQ、DA 和四字节 DI。
4. 结构化解析终端登录、终端心跳和全部确认/否认。
5. 对其他合法 AFN 或 DI 展示公共字段及剩余原始应用数据。
6. 在手动解析、自动检测、多帧提取、字段树和全局日志预览中贯通该协议。
7. 使用从 `Terminal3.log` 提取的黄金样本建立可重复回归测试，并以完整日志做交付验收。

## 3. 非目标

第一阶段不实现：

- 完整附录 A–P 数据字典；
- XML 数据字典、加载器或协议同步；
- 智能组帧或反向编码；
- 应用层分片重组；
- PW、Tp、密文、文件内容和嵌套规约的结构化展开；
- 对 AFN 12 任务数据内部的多个信息体进行推测式解析；
- 与本协议无关的解析器重构或 UI 调整。

## 4. 命名与兼容策略

用户界面统一显示“南网计量上行规约”。代码模块使用 `csg_upstream`，解析器使用 `CsgUpstreamParser`。

协议实现依据为 2026 版 V1.0，但报文内携带的规约版本号只作为数据值展示，不作为接受或拒绝帧的条件。真实日志中版本号为 `0110` 的登录帧必须正常解析。现有 `ProtocolType` 数值保持不变，新协议追加为数值 8，避免破坏已保存的协议选择设置。

## 5. 协议边界

### 5.1 帧格式

链路帧按以下顺序解析：

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| 起始字符 | 1 字节 | 固定 `68H` |
| 长度 L | 2 字节 | BIN，小端；表示用户数据区长度 |
| 重复长度 L | 2 字节 | 必须与第一个 L 完全一致 |
| 第二起始字符 | 1 字节 | 固定 `68H` |
| 控制域 C | 1 字节 | DIR、PRM、FCB/ACD、FCV、链路功能码 |
| 地址域 A | 7 字节 | A1 三字节、A2 三字节、A3 一字节 |
| 链路用户数据 | 可变 | AFN、SEQ、一个或多个信息体及可选尾部字段 |
| 校验和 CS | 1 字节 | 用户数据区全部字节的八位算术和 |
| 结束字符 | 1 字节 | 固定 `16H` |

完整帧长度为 `L + 8`。解析器只消费第一帧允许的字节数，因此同一输入中后续完整帧仍由现有多帧循环继续处理。

### 5.2 应用层公共字段

第一阶段解析以下公共字段：

- AFN：一字节，并映射当前规范中的应用功能名称；
- SEQ：TpV、FIR、FIN、CON 和低四位帧序号；
- DA：DA1 与 DA2，并计算 p0、单个信息点或位图信息点集合；
- DI：按低字节在前恢复为八位十六进制编码。

第一阶段只结构化展开第一个信息体。只有命中已实现 DI 且剩余长度满足该 DI 的定义时，才继续解释数据内容。

## 6. 组件设计

### 6.1 新协议模块

新增目录 `src/protocols/csg_upstream/`：

- `CsgUpstreamDef.h`：定义 `CsgUpstreamField`、首批 DI 常量和解析所需的小型数据结构；
- `CsgUpstreamParser.h`：声明严格帧校验、帧长获取、完整字段解析和概要提取接口；
- `CsgUpstreamParser.cpp`：实现链路层、应用层公共字段、首批 DI 和未知数据降级。

解析器沿用现有协议模块的返回模型：每个字段包含名称、值、描述、原始偏移、长度和缩进层级。数据项映射直接保留在解析器实现中，不创建只服务于三个 DI 的额外注册表抽象。

### 6.2 协议检测器

`ProtocolDetector` 追加 `ProtocolCsgUpstream = 8`，并增加：

- 严格识别分支；
- `L + 8` 帧长计算分支；
- 协议显示名称分支。

新协议属于带校验和的严格协议，应放在只做长度验证的 IEC 104 之前。它必须依靠双长度、固定第二起始符、CS 和结束符共同识别，不能只根据首字节 `68H` 判断。

### 6.3 后端接入

`LogBackend` 增加：

- `parseSingleFrame()` 中的新解析器分支；
- 全局日志预览中的新概要分支；
- 当前协议名称处理。

解析器负责字节语义，`LogBackend` 只负责把字段映射到现有结果模型，不在后端重复协议判断或 DI 解析。

### 6.4 UI 与构建接入

`CMakeLists.txt` 纳入新协议源文件和可选测试目标。

`qml/Main.qml` 中以下列表追加“南网计量上行规约”：

- 主解析区协议选择；
- 预置报文分类；
- 预置报文管理分类。

第一阶段不把新协议加入 `listSmartFramingProtocols()`，不修改智能组帧页面，也不加入 `ProtocolSyncManager` 的 XML 文件清单。

## 7. 严格校验规则

以下任一条件成立时，不得识别为本协议：

1. 数据短于最小合法帧；
2. 第一个或第二个起始字符不是 `68H`；
3. 两个长度值不一致；
4. L 小于控制域、地址域和最小应用层公共字段所需长度；
5. 当前输入不足 `L + 8` 字节；
6. 用户数据区八位算术和与 CS 不一致；
7. 计算得到的第一帧末尾不是 `16H`。

输入超过第一帧长度不属于错误。校验和帧长函数只针对第一帧，后续字节交还现有多帧处理流程。

## 8. 首批数据项

### 8.1 终端登录

- AFN：`02H`
- DI：`E0001000H`
- 显示名称：终端登录
- 最小结构化字段：规约版本号

版本号按规范的低字节在前规则还原。真实样本中的数据 `10 01` 显示为 `0110`。若安全模块标志或终端时间缺失，已解析字段仍保留，并将剩余规范字段标记为缺失；不得越界读取。

### 8.2 终端心跳

- AFN：`02H`
- DI：`E0001001H`
- 显示名称：终端心跳
- 数据内容：无

存在额外应用数据时不猜测其含义，作为未解析尾部显示。

### 8.3 全部确认/否认

- AFN：`00H`
- DI：`E0000000H`
- 显示名称：全部确认/否认
- 数据内容：一字节结果码

结果码 `00H` 显示“全部肯定”，`01H` 显示“全部否定”，其他值显示“未知确认码”并保留十六进制值。

## 9. 未支持数据降级

对通过严格帧校验、但 AFN 或 DI 尚未支持的报文：

1. 协议识别保持成功；
2. 链路层、AFN、SEQ、DA 和首个 DI 正常显示；
3. 剩余字节作为“未解析应用数据”展示，保留准确偏移、长度和完整十六进制；
4. 概要显示方向、地址、帧序号、AFN、DI 和“暂未展开”；
5. 不扫描剩余字节寻找看似合法的 DI，不猜测 PW、Tp 或多个信息体边界。

这种降级行为是第一阶段的正常能力，不记录为整帧解析错误。

## 10. 数据流

1. 现有输入层从手动输入或日志行中提取十六进制候选并转换为 `QByteArray`。
2. 自动模式调用 `ProtocolDetector`；手动模式使用用户选择的协议枚举。
3. 检测器在候选起点及现有允许的滑动偏移内执行严格校验。
4. `getFrameLength()` 返回第一帧的 `L + 8`。
5. `LogBackend` 将精确帧切片传给 `CsgUpstreamParser`。
6. 解析器返回字段列表或概要。
7. 后端复用现有模型更新字段树、差异视图和全局预览。
8. 输入中有后续帧时，现有多帧循环继续执行。

## 11. 测试设计

### 11.1 小型黄金样本

从 `Terminal3.log` 提取最小、可审查的固定样本，覆盖：

- 登录帧：`681200120068c92531440304110002700000001000e01001ee16`；
- 确认帧：`681100110068002531440304110100600000000000E000f316`；
- 一条真实心跳帧；
- 一条校验有效但 AFN 12 数据未支持的真实帧；
- 分别破坏重复长度、第二个 `68`、CS、结束符以及截断长度的负向帧。

有效样本必须断言协议识别结果、帧长、概要字段、解析字段值以及每个关键字段的偏移和长度。未知 DI 样本必须断言公共字段存在且原始应用数据完整。

### 11.2 测试目标

新增项目专用的轻量 C++ 测试目标，直接链接 Qt Core 和新解析器，不引入新的生产依赖。测试构建开关与第三方 libssh2 的 `BUILD_TESTING` 隔离，避免当前全局关闭第三方测试的设置吞掉协议测试。

### 11.3 完整日志验收

以“每行最大连续十六进制候选”为提取口径，当前 `Terminal3.log` 的基线为：

| 项目 | 数量 |
| --- | ---: |
| 十六进制候选 | 485 |
| 严格校验有效帧 | 480 |
| 应拒绝帧 | 5 |
| AFN 00 | 240 |
| AFN 02 | 115 |
| AFN 12 | 125 |
| `E0000000` | 240 |
| `E0001001` | 114 |
| `E0001000` | 1 |

程序实际打开并扫描 `Terminal3.log` 后，识别数量和分类必须与该基线一致。抽查登录、心跳、确认和未知 AFN 12 四种字段树与日志中的既有解析说明一致。

### 11.4 回归与性能

- 运行新协议解析测试；
- 运行仓库已有测试；
- 构建主程序；
- 验证自动检测和显式选择两条路径；
- 在同一机器和同一日志上记录修改前后扫描耗时，确认新增严格检测器没有造成明显回退；
- 至少抽查一条现有 `68H` 开头协议样本，确认不会被新协议抢先误判。

## 12. 完成标准

第一阶段仅在以下条件全部满足时完成：

1. 三个首批 DI 按设计解析；
2. 公共链路和应用层字段具有正确值、偏移和长度；
3. 未支持 AFN/DI 安全降级且整帧保持识别成功；
4. 五类结构错误均被拒绝；
5. `Terminal3.log` 的 480 有效帧与 5 个拒绝帧统计一致；
6. 自动检测、手动解析、多帧处理、字段树和全局预览全部贯通；
7. 现有协议枚举编号、协议检测和智能组帧功能不受影响；
8. 未引入完整字典、XML 同步、组帧或无关重构。

## 13. 实施前置条件

用户将在规划完成后提交当前工作区已有修改。正式实施前必须重新检查：

- 工作区是否干净；
- 当前提交是否包含规划期间观察到的 CMake、后端和 QML 变化；
- 构建预设和现有测试是否可运行；
- 本设计中的文件路径和接入点是否仍与提交后的基线一致。

如提交后的基线发生结构变化，只调整实施计划中的文件位置，不扩大本设计范围。
